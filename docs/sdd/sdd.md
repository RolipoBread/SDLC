# Software Design Description (SDD) для проекта BarterHub

## 1. Введение
Настоящий документ описывает архитектуру и дизайн веб-приложения «BarterHub» — платформы для обмена товарами без денег (бартера). Документ предназначен для команды разработки и служит руководством при реализации проекта.

## 2. Архитектура системы
Система построена по клиент-серверной архитектуре с разделением на Frontend и Backend.

### 2.1. Технологический стек
*   **Backend:** Java 17+ (Spring Boot) — обеспечивает надежность, безопасность и удобную работу с базой данных.
*   **Frontend:** React (TypeScript) — обеспечивает быстрый и отзывчивый пользовательский интерфейс.
*   **База данных:** PostgreSQL — реляционная СУБД для хранения данных пользователей, объявлений и офферов.
*   **Контейнеризация:** Docker — для упрощения развертывания.

### 2.2. Компоненты системы
1.  **API Gateway (Spring Boot):** Обрабатывает входящие HTTP-запросы от Frontend, выполняет аутентификацию (JWT), маршрутизацию и валидацию данных.
2.  **Модуль пользователей:** Регистрация, авторизация, управление профилем (включая номер телефона, скрытый до сделки).
3.  **Модуль объявлений:** Создание, редактирование и просмотр товаров. Включает загрузку фото (интеграция с S3) и указание желаемого товара для обмена.
4.  **Модуль офферов:** Обработка предложений обмена, смена статусов («На рассмотрении», «Отказ», «Торг», «Согласен»), логика раскрытия контактов.
5.  **Модуль рекомендаций:** Алгоритм подбора объявлений на основе истории просмотров и предыдущих офферов пользователя.

## 3. Системные требования

### 3.1. Функциональные требования
*   **FR-1:** Система должна обеспечивать регистрацию пользователей с обязательной валидацией номера телефона.
*   **FR-2:** Пользователь должен иметь возможность создать объявление с загрузкой фотографии и указанием желаемого варианта обмена.
*   **FR-3:** Пользователь должен иметь возможность отправить оффер (предложение обмена) на чужое объявление.
*   **FR-4:** Владелец объявления должен иметь возможность изменить статус оффера на «Отказано», «Торг» или «Согласен».
*   **FR-5:** При статусе «Торг» отправитель оффера должен иметь возможность отредактировать свое предложение (добавить товар/условия).
*   **FR-6:** Система должна скрывать номера телефонов обеих сторон до момента подтверждения оффера (статус «Согласен»).
*   **FR-7:** Система должна отображать рекомендательную ленту объявлений на основе интересов пользователя.

### 3.2. Нефункциональные требования
*   **NFR-1 (Безопасность):** Пароли пользователей должны храниться в виде хешей (BCrypt). Номера телефонов передаются только по HTTPS.
*   **NFR-2 (Производительность):** Время загрузки главной страницы (ленты) не должно превышать 2 секунд.
*   **NFR-3 (Доступность):** Интерфейс должен быть адаптивным (Mobile-first) и корректно отображаться на устройствах с шириной экрана от 375px.

## 4. Взаимодействие компонентов
Frontend (React) взаимодействует с Backend (Spring Boot) через REST API. Аутентификация осуществляется с помощью JWT-токенов. Загрузка изображений происходит напрямую в S3-хранилище (или через прокси бэкенда). Уведомления о смене статуса оффера могут быть реализованы через WebSocket (опционально) или при следующем запросе пользователя.
